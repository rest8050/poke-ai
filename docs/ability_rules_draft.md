# 특성 EXEC 규칙 표 — 초안 v1 (상위 20종 중 규칙으로 계산 가능한 14종)

상태: **초안 v1.1, 사람 검토 전.** 구현 없음. (v1.1: 세트 추정 확률 포함, 스피드 규칙 확대, 위협 명시 열, fm_edge를 양쪽 토큰에 적용으로 결정 반영) 효과 값과 조건은 `pokemon-showdown/data/abilities.ts`(및 `sim/battle-actions.ts`) 소스에서 읽었다.
이 문서는 특성을 분류하지 않는다. **특성 → (규칙, 매개변수) → 입력 특징**의 표이고, `Matchup`이 forward 때 계산해서 모델에 수치로 준다. 모델이 표를 읽지 않는다.
범위 밖: 규칙으로 값을 못 내는 반응형 효과 6종(pressure, dancer, harvest, justified, defiant, competitive)은 이 문서에서 다루지 않고 기존 훅/설명문 특징(`entity_features`)에 맡긴다. 단 defiant/competitive가 위협에 반응한 *결과*는 아래 intimidate 규칙에 포함한다.

## 1. 대상과 규모

## 2. 현재 코드 사실 (이 표가 끼워질 자리)

- `Matchup`(`src/core/matchup.py`): 공격기만 계산(변화기 4채널은 전부 0), 입력은 저장된 텐서(능력치, 랭크, 타입, 특성/도구 id, HP, 기술 위력/분류/타입)와 `field_vec`. 이미 있는 규칙: 타입 상성, 자속/테라, 화상, 부유류 면역(`IMMUNE_ABILITIES`), 풍선, 천진(공/방 랭크 무시), 장판 진입 피해(`entry_frac`).
- 스피드: `Matchup.forward`의 `spd_my/spd_opp`는 능력치 비율만 본다(날씨, 트릭룸, 마비, 도구 없음). 인코더의 `priority_speed_edge`(기술 수치 45번 열)는 우선도 등급 차이와 종족값 스피드를 비교하고 **트릭룸 반전은 반영**하지만, 랭크, 마비, 날씨 특성, 도구는 반영하지 않는다. 이 값은 npz에 저장되므로 바꾸려면 데이터 재빌드가 필요하다. 따라서 A단계의 스피드/우선도 규칙은 저장된 값을 건드리지 않고 `Matchup`이 forward 때 새로 계산한다.
- `Matchup.forward`는 현재 `field_vec`를 받지 않는다(`entry_frac`만 따로 받음). 스피드 규칙에는 날씨 플래그가 필요해서 인터페이스 변경이 필요하다.

## 3-2. 스피드/선공 규칙 (`fm_edge`, A단계)

유효 스피드와 유효 우선도로 "이 기술이 상대 활성보다 먼저 나가는가"를 계산한다. 인코더의 `priority_speed_edge`(저장된 45번 열)를 대체하는 forward 시점 계산이며, 저장된 열은 건드리지 않는다(다음 재빌드 때 제거 대상).

| 요인 | 규칙 | 읽는 입력 |
|---|---|---|
| 스피드 능력치 | 기존 `_stats`(내 쪽 실능력치, 상대 쪽 종족값 + 세트 추정 배율) | `num[..., 11:17]`, 세트 추정 `mult` |
| 랭크 | `_stage(스피드 랭크)` 곱 | `num[..., 7]` |
| 마비 | ×0.5 (9세대) | `cat[..., 4] == par` |
| 구애스카프 | ×1.5. 내 쪽은 도구 id로, 상대는 세트 추정 도구 확률 `p(choicescarf)` 기대값 | `cat[..., 0]`, 세트 추정 `item` |
| 순풍 | 해당 진영 ×2 | `field_vec` 26(내 쪽), 38(상대 쪽) |
| 날씨 특성 | chlorophyll(쾌청 ×2), swiftswim(비 ×2). 같은 규칙 종류이므로 sandrush, slushrush, surgesurfer 등은 표 행만 추가 (소스 확인 후) | `field_vec` 0, 2, 세트 추정 특성 확률 |
| 트릭룸 | 같은 우선도 등급일 때 스피드 순서 반전 | `field_vec` 10 |
| 우선도 | 기술의 저장된 우선도(기술 수치 3번 열 × 7), prankster이면 변화기 +1, 악 타입 대상에게 실패 | `mv[..., 3]`, 특성 확률 |

출력은 `fm_edge = E[sign]` ∈ [−1, +1] (+1 확실히 먼저, −1 확실히 나중, 0 동률·불명). 상대 쪽 불확실 요인(스카프, 날씨 스피드 특성, prankster)의 조합(각각 있다/없다)별로 순서를 비교해 세트 추정 확률 가중 평균을 낸다. 상대가 드러낸 기술 중 최고 우선도를 상대 우선도로 쓰고(기존과 같음), 안 드러낸 기술은 0으로 본다.
**양쪽 토큰에 모두 준다**: 내 포켓몬 6마리의 기술 칸은 상대 활성을 기준으로, 상대 포켓몬 6마리의 드러난 기술 칸은 내 활성을 기준으로 계산한다(인코더의 기존 규약과 같음).

## 3-3. 상대 특성/도구의 세트 추정 확률 처리 (A단계 기본)

- 상대 특성 분포 `q`: 공개됐거나 종의 가능 특성이 1개면 원핫, 아니면 세트 추정 `ability` 로짓에서 특수 칸(빈칸, `<unk>`, 숨김)을 뺀 softmax. 내 쪽은 항상 원핫. 세트 추정 출력은 detach이므로 학습 경로가 늘지 않는다.
- 규칙마다 특성 의존 값을 어휘 크기의 표(`f[특성]`)로 두고 기대값 `Σ q[a]·f[a]`로 계산한다. 예: 타입 t에 대한 방어측 배율 `F_def[a, t]`(부유 땅 0, 물먹기 물 0, 풀먹기 풀 0, 두꺼운지방 불/얼음 0.5)와 기대 배율 `q @ F_def[:, t]`. 이로써 기존 `IMMUNE_ABILITIES` 면역도 상대 특성이 미공개일 때 확률로 반영된다(지금은 미공개이면 면역 없음으로 처리).
- 확률 합성: KO는 `P_KO`처럼 확률로(옹골참은 `1 − q[sturdy]·[만피]` 항), 배율은 기대값으로.
- 측정(학습에 안 쓴 세트, 나중에 특성이 공개되는 상대 포켓몬 5,851 시점): 세트 추정 top-1 정확도 **0.940**, 정답 확률 평균 0.930, 엔트로피 0.107(무작위 기준 정답 확률 0.399). 종별 가능 특성으로 제한해도 0.940 그대로라 **별도 마스크는 불필요**(세트 추정이 종을 이미 조건으로 쓴다). 한계: 공개된 특성은 발동/추론되는 특성에 치우친 표본이라, 끝까지 안 드러나는 특성의 정확도는 이보다 낮을 수 있다.
- 도구 세트 추정(같은 방식, 나중에 도구가 공개되는 21,478 시점): 전체 도구 top-1 0.564, 정답 확률 평균 0.488, 엔트로피 0.912로 특성보다 훨씬 불확실하다. 스카프는 공개된 도구 중 0.6%(127개)뿐이고, 세트 추정의 p(스카프)는 평균 0.004~0.009로 사실상 0에 가까우며(AUC 0.76, 구애 계열 0.73) 구간별 보정에서도 신호가 거의 없다. 결론: 스카프 규칙은 기대값 형태로 넣되(내 쪽은 정확, 상대는 확률 ≈ 0) 효과는 기대하지 않는다. 상대 스피드를 실제로 좁히는 건 도구 확률이 아니라 **관측된 선공 순서**(어느 쪽이 먼저 움직였나)로 추론하는 방식이며, 별도 과제로 남긴다.

## 4. 새 입력 열 (초안)

| 열 | 형태 | 의미 |
|---|---|---|
| `fm_edge` | 기술 토큰 12×4 각각 1 (`mv_extra` +1) | 이 기술이 반대편 활성보다 먼저 나갈 기대값 (3-2장) |
| `exit_heal` | 활성 스칼라 1 | 지금 활성이 교체되어 나갈 때 회복량 `min(1/3, 1 − HP)` × P(regenerator) |
| `entry_opp_atk`, `entry_opp_spa`, `entry_opp_spe` | 교체 후보별 각 1 (후보 특징 +3) | 이 후보가 들어올 때 상대 활성의 공격/특공/스피드 배율(위협과 상대 특성 결과 표, 상대 특성은 확률 기대값) |

그 외 규칙은 기존 D/O 채널(배율, 데미지 비율, KO)과 `spd_my/spd_opp` 값만 정확하게 바꾼다. 위협은 후보의 D 채널 값에도 반영하고(상대 공격이 약해진 만큼), 명시 열로도 따로 준다.
입력 열이 늘고 값 분포가 바뀌므로 **모델은 재학습**이 필요하다. A단계는 데이터 재빌드가 필요 없다.

## 5. 구현 순서 (제안)

1. `Matchup.forward`에 `field_vec`를 넘기는 인터페이스 정리.
2. A단계 규칙 구현, 규칙마다 소스 경계값 단위 테스트.
3. B단계: 인코더 효과 열 확장 + 데이터 재빌드 + 규칙 구현.
4. 같은 데이터로 `v6`(합법 비트 수정만 반영) 대조군과 비교.

## 6. 테스트 (소스 경계값)

- technician: 위력 60 → ×1.5, 위력 65 → 변화 없음.
- thickfat: 불꽃/얼음 ×0.5, 물 변화 없음.
- sturdy: 만피에서 KO 가능한 데미지도 `ko=False`, HP 99%에서는 `ko=True`.
- chlorophyll/swiftswim: 쾌청/비에서만 ×2, 다른 날씨에서는 ×1.
- prankster: 변화기 우선도 +1, 공격기 +0, 악 타입 대상은 실패 표시.
- intimidate: 후보 입장 시 공격 −1(물리 데미지 ×2/3), clearbody 상대는 0, defiant 상대는 +1.
- regenerator: HP 100%면 0, HP 50%면 1/3, HP 80%면 0.2.
- fm_edge: 우선도 등급이 다르면 스피드와 무관(트릭룸도 무관), 같으면 유효 스피드 비교 (마비 ×0.5, 랭크, 순풍 ×2, 스카프 ×1.5, 날씨 특성 ×2가 각각 순서를 바꾸는 경계 사례), 트릭룸이면 반전, 장난꾸러기 변화기는 +1이고 악 타입 대상은 실패 표시.
- 세트 추정 기대값: 상대 특성이 미공개이고 q(thickfat)=0.5이면 불꽃 기술 기대 배율 0.75, 원핫이면 0.5, 공개된 특성은 세트 추정 입력과 무관.
- 위협 명시 열: 후보가 intimidate이고 상대가 defiant이면 `entry_opp_atk`은 1보다 큰 값(+1 랭크 효과), clearbody이면 1.

## 7. 통과선 (사전 등록)

- 날씨 연동 특성 묶음의 일치율 격차 −0.043이 줄어드는지 (쓱쓱/엽록소 규칙의 직접 효과).
- 변화기를 교사가 고른 결정의 일치율 0.535가 오르는지 (prankster `fm_edge`의 직접 효과는 일부만).
- 교체 선택이 가장 약하므로(일치율 0.452), intimidate/regenerator 규칙이 교체 결정 일치율을 올리는지.
- 전체 KL이 나빠지지 않을 것 (+0.005 이내), 다른 특성 묶음이 나빠지지 않을 것.
- 특성 소거 민감도가 오르는지 (지금 0.026~0.046).
- 비교는 항상 같은 데이터로 학습한 `v6` 대조군 대비이며, 승률은 시드 변동(약 ±5pp) 때문에 최종 확인용으로만 쓴다.

## 8. 결정 사항과 남은 확인

결정됨 (v1.1):
1. 상대 특성 미공개는 세트 추정 확률 기대값으로 처리한다 (3-3장, 측정 근거 포함).
2. 스피드 규칙은 날씨 특성 + 마비, 랭크, 스카프, 순풍, 트릭룸까지 한꺼번에 넣는다 (3-2장).
3. 위협 효과는 후보 D 채널 반영과 명시 열(`entry_opp_*`) 둘 다 준다.
4. `fm_edge`는 내 토큰과 상대의 드러난 기술 토큰 양쪽에 준다.

남은 확인:
- (완료) 도구 세트 추정 정확도 측정: 스카프 신호가 사실상 없음 (3-3장).
- 날씨 스피드 특성 중 sandrush, slushrush, surgesurfer 등 표 행 소스 확인.
- 저장된 `priority_speed_edge`(45번 열)를 같이 입력으로 두면 중복이 생김: 재학습 때 이 열을 0으로 마스킹할지 그대로 둘지.

## 9. 예약 (이 표의 확장)

`IGNORE_TARGET_ABILITY`(moldbreaker: `breakable` 면역/보정 무효화), `STATUS_IMMUNE`(불면 등), `REFLECT_STATUS`(magicbounce), `ATTACK_MULT`(hugepower, guts), `DAMAGE_MULT_COND`(multiscale 등). 상위 20종 밖이고 변화기 적용 가능성 표와 함께 별도 문서로 다룬다.
